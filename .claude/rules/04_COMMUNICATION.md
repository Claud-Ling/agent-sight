# COMMUNICATION.md - 沟通风格指南

## §适用范围

这份指南服务项目开发协作，覆盖需求澄清、设计文档、实施计划、补丁说明、调试记录和代码 review。

## §基本风格

务实、理性、克制。结论前置，证据跟上。不要用营销词、空泛 praise 或文学化比喻代替工程判断。

结论前置还是按顺序展开，取决于读者已经掌握了多少上下文。如果你和读者在同一个 bug 或任务里继续讨论（在线 chat、PR 评论），结论前置，证据精简跟上。如果读者第一次接触这个问题（issue tracker、调试记录、移交说明），按问题分析的顺序展开（见下），让他们自己重建证据链，不要直接抛根因。没有验证的部分就明确写"未验证"，不要暗示已经通过。

## §表达对象要具体

优先使用真实对象名，而不是"这块逻辑""某个配置""某处代码"这种泛指。

当问题涉及范围判断时，明确它属于哪个模块、哪个 layer 还是跨模块；不要把边界混成一句笼统判断。

## §写问题分析

问题分析按下面的顺序写：

1. 现象：看到什么失败、异常或行为偏差。现象段必须绑定可复现坐标：运行环境（本地/Docker/服务器）、对应的版本或 commit、失败发生在哪个阶段（构建/测试/部署/运行时）。
2. 定位：证据来自哪些文件、日志、接口或调用链。
3. 根因假设：为什么这些证据指向这个原因。
4. 验证：已经跑过什么命令、看过什么输出、还有什么未验证。
5. 影响范围：改动会影响哪个模块、接口或组件。

观察和推测要分开写。日志、代码、配置、命令输出属于观察；根因判断、风险判断和下一步动作属于推测或结论。

## §写实现与补丁说明

补丁说明至少覆盖四件事：

1. 改了什么。
2. 为什么放在这里改，而不是在别的层级修。
3. 明确没有改什么，避免读者误判范围。
4. 用什么方式验证，预期结果是什么。

不要把 build-time、test-time、runtime 和 deploy-time 的问题混为一谈。说明改动收益时，用可核对的行为变化，不用"更稳""更优雅"这类形容词收口。

## §写设计与计划

设计和计划先写边界，再写任务，再写验证。边界至少包括目标、非目标、影响层级和依赖条件。

当内容天然是并列结构时，显式编号，不要让读者自己数。需要回指时，用"第一点""第二步"这类稳定锚点。

## §写 review

review 先给 findings，再给背景。每条 finding 至少说明风险、触发条件和落点文件，并标注严重级别：🔴 高（阻塞 build / 核心接口 / 数据正确性）、🟡 中（影响特定场景或模块，有 workaround）、🟢 低（命名、风格、文档等不阻塞）。能给真实路径和对象名，就不要退回抽象概念。

## §用词约束

- 不用"应该可以""大概没问题""看起来像"这类弱判断冒充结论。
- 不用"击穿""拆解""闭眼编""很稳"这类口语化比喻做工程判断。
- 不用"结构性"这类空泛词替代具体机制。
- 不把观察、结论和行动建议写在一句混合语里。

## §结构约束

- 长结论后紧跟最小证据。
- 并列事项显式编号。
- 未验证项单独标注，不埋在段落中间。

## §文件交叉引用规范

本节定义知识文件之间的交叉引用机制，用于构建可递归导航的知识图谱。适用对象：`.claude/rules/skills/`、`.claude/rules/axioms/`、`.claude/docs/` 及 `.claude/skills/` 下的所有知识文件。

### §Section 标记

每个章节标题使用 `§` 前缀（如 `## §Quick Reference`、`## §核心流程`），便于 `grep "§SectionName"` 精确定位行号。

### §Related: 引用行

每个章节末尾，如有关联内容在其他文件/章节，**必须**加 `Related:` 行：

```
Related: [03_WORKSPACE.md §文件生命周期管理] [05_SKILLS_INDEX.md §BestPractice]
```

章节内正文中，提到其他文件的概念时用内联引用：

```
具体写法参考 [bestpractice_01-skill_writing.md §输出规格]。
```

### §引用格式

- **文件级引用**：`[filename.md]`
- **章节级引用**：`[filename.md §SectionName]`
- 引用路径相对于 `.claude/rules/` 目录（`.claude/rules/` 内的文件互相引用）或 repo 根（`.claude/skills/` 内的文件引用外部）
- 引用目标文件不需要相对于当前文件计算路径——统一用文件名（同一目录下）或相对 repo 根的路径

### §Section 命名约束

- **一旦被其他文件引用，禁止随意改名**。改名必须全局搜索 `grep -r "旧名"` 更新所有引用
- Section 命名用中文或英文均可，但要简洁、稳定、不容易因为内容微调而需要改名
- 如果某个 section 的内容变化很大、标题不再匹配，先更新所有引用再改名

### §跳转深度

- 避免超过 **3 跳**的引用链。若信息过分分散，在 `03_WORKSPACE.md` 增加直达路由条目
- 常见高价值引用边（如 `skill → axiom`、`skill → skill`）优先建立

### §Quick Reference 中的 Related files

需要高频跳转的文件，在 `§Quick Reference` 中包含 `Related files:` 行：

```
Related files: [03_WORKSPACE.md] [05_SKILLS_INDEX.md] [bestpractice_01-skill_writing.md]
```
